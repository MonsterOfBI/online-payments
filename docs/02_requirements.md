# 2. Требования

## 2.1. Пользовательские истории
**US-01 (Must). Оплата без двойного списания.** Как покупатель, я хочу, чтобы повторное нажатие «Оплатить» не списывало деньги второй раз.
- *Given* по заказу уже создан платёж в статусе `pending`, *When* покупатель снова нажал «Оплатить» в течение 10 мин, *Then* бэкенд отправляет запрос с тем же ключом идемпотентности и получает тот же платёж.
- *Given* предыдущая попытка `canceled`, *When* покупатель нажал «Оплатить», *Then* создаётся новый платёж с новым ключом (`{order_id}-{attempt_no}`).

**US-02 (Must). Оплата по QR СБП на мобильном.** Как покупатель с телефона, я хочу оплатить через приложение своего банка, чтобы не вводить карту и не проходить 3-DS.
- *Given* устройство mobile и сумма ≤ лимита СБП, *When* открыт экран оплаты, *Then* СБП показан первым способом.
- *Given* выбран СБП, *When* платёж создан, *Then* покупатель видит список банков (deeplink), а на десктопе — QR-код.
- *Given* покупатель не подтвердил оплату за 10 минут, *Then* платёж `canceled` (`expired_on_confirmation`), заказ остаётся `awaiting_payment`, предложен другой способ.

**US-03 (Must). Мгновенный статус заказа.** Как склад, я хочу видеть оплату сразу, чтобы собирать заказ без задержки.
- *Given* пришёл webhook `payment.succeeded`, *When* бэкенд перепроверил статус через `GET /payments/{id}`, *Then* заказ `paid` не позднее 1 минуты после события.
- *Given* тот же webhook пришёл повторно, *Then* заказ не меняется, ответ 200, событие логируется как повтор.
- *Given* webhook не пришёл за 10 минут после создания платежа, *Then* бэкенд сам запрашивает статус (страховочный опрос).

**US-04 (Must). Понятный отказ.** Как покупатель, я хочу понять, почему оплата не прошла, и сразу попробовать другой способ.
- *Given* `cancel_reason = insufficient_funds`, *Then* текст «Недостаточно средств. Попробуйте другую карту или СБП» и кнопка СБП.
- *Given* `cancel_reason = fraud_suspected`, *Then* нейтральный текст без раскрытия причины, предложен СБП.

**US-05 (Must). Возврат по кнопке.** Как оператор поддержки, я хочу оформить полный или частичный возврат из админки, чтобы покупатель получил деньги в тот же день.
- *Given* заказ `paid` и сумма возврата ≤ оплаченной минус уже возвращённое, *When* оператор нажал «Вернуть», *Then* создаётся возврат с ключом идемпотентности = id заявки, статус заказа `refunded`/`partially_refunded` после `refund.succeeded`.
- *Given* сумма возврата больше доступной, *Then* кнопка неактивна, ошибка 422 `REFUND_AMOUNT_EXCEEDED`.

**US-06 (Should). Чек на возврат.** Как бухгалтер, я хочу, чтобы при возврате формировался чек возврата прихода (54-ФЗ).

**US-07 (Could). Оплата цифровым рублём.** Как покупатель, я хочу оплатить цифровым рублём (после подключения способа у провайдера). — требования в `docs/04_sbp_digital_ruble.md`.

## 2.2. Бизнес-правила
| ID | Правило |
|---|---|
| BR-01 | Ключ идемпотентности создания платежа: `{order_id}-{attempt_no}`; новый номер попытки — только после `canceled` |
| BR-02 | Статус заказа меняется только после перепроверки статуса платежа через `GET` (webhook может быть подделан) |
| BR-03 | Время на подтверждение платежа — 10 минут, после — `expired_on_confirmation` |
| BR-04 | Возврат: сумма возвратов по платежу ≤ сумме платежа; ключ = id заявки на возврат |
| BR-05 | Склад получает заказ только в статусе `paid` |
| BR-06 | На мобильном СБП показывается первым; на десктопе — карта первой, СБП вторым (QR) |

## 2.3. Нефункциональные требования
| ID | Требование |
|---|---|
| NFR-01 | Обработчик webhook отвечает 200 за ≤ 3 с, тяжёлую обработку выполняет асинхронно |
| NFR-02 | Обработка webhook идемпотентна: повтор не меняет данные |
| NFR-03 | Данные карт магазин не хранит и не видит (платёжная форма провайдера, PCI DSS на стороне провайдера) |
| NFR-04 | Секретный ключ магазина — только на бэкенде, в хранилище секретов |
| NFR-05 | Все вызовы к платёжному сервису логируются (без персональных данных) с id запроса и ключом |
| NFR-06 | Таймаут вызова создания платежа 10 с; при таймауте — повтор с тем же ключом, не более 3 раз |

## 2.4. KPI
| KPI | Формула | Baseline | Цель |
|---|---|---|---|
| Конверсия оплаты (mobile) | заказы с succeeded / заказы, перешедшие к оплате | 80,2 % | 86 % |
| Доля двойных списаний | заказы с > 1 succeeded / оплаченные заказы | 0,60 % | 0 % |
| Задержка статуса, p95 | `paid_at` в магазине − `finished_at` в сервисе | 28,7 мин | ≤ 1 мин |
| Медиана времени возврата | succeeded_at − requested_at | ~48 ч | ≤ 4 ч |
| Доля оплат через СБП | платежи СБП / все succeeded | 0 % | 25 % |

## 2.5. Тест-кейсы (тестовый магазин ЮKassa)
> Тестовые карты из документации ЮKassa (yookassa.ru/developers/using-api/testing). В тестовом режиме работают карты и кошелёк ЮMoney; **СБП проверяется только в боевом магазине** — поэтому кейсы СБП описаны, но не выполнены.

| ID | Сценарий | Данные | Ожидаемый результат |
|---|---|---|---|
| TC-01 | Успешная оплата картой с 3-DS | карта «Мир» 2200 0000 0000 0004 | `succeeded`, webhook `payment.succeeded`, заказ `paid` |
| TC-02 | Отказ: недостаточно средств | карта 5555 5555 5555 4600 | `canceled`, `insufficient_funds`, текст по US-04 |
| TC-03 | Двойное нажатие «Оплатить» | два POST с одним ключом за 3 с | один платёж, второй ответ — тот же `id` |
| TC-04 | Повторный webhook | отправить тот же webhook дважды | заказ не меняется, 200 |
| TC-05 | Webhook не пришёл | отключить приём уведомлений | через 10 мин страховочный `GET`, заказ `paid` |
| TC-06 | Полный возврат | платёж из TC-01 | `refund.succeeded`, заказ `refunded`, чек возврата |
| TC-07 | Частичный возврат + превышение | вернуть 40 %, потом 70 % | первый `succeeded`, второй — 422 `REFUND_AMOUNT_EXCEEDED` |
| TC-08 | СБП: не подтвердил за 10 минут | боевой магазин | `canceled`, `expired_on_confirmation` |
